# SQL Judge — Executable implementation plan

## Goal
Build a production-quality offline-first desktop SQL learning tool by **extending the existing `create-tauri-ui` scaffold**, preserving Vite + shadcn b0 + dashboard/invoke/size-optimization/release-workflow selections. All implementation is future work; this kit supplies specs, tests for pack format and task instructions.

## Work partition and dependency order
```
P0  inspect generated app + baseline + contract verification
            ↓
P1  judge-core comparator ↔ PostgreSQL disposable test runner
            ↓
P1  minimal Problem -> Monaco -> Run -> Submit -> Verdict
            ↓
P2  managed pack environments, import, metadata/history, cancellation
            ↓
P3  external PostgreSQL/MSSQL read-only connections + schema browser
            ↓
P4  platform runtime bundling, SQL Server isolated judge (separately approved)
```

Parallel work only after interface contracts are frozen: frontend UI and pure Judge comparator may run concurrently; packs generated by agents may run concurrently once package schema validated; never parallel shared migrations/workflow/root manifests or admin lifecycle logic.

## Gates
- **Gate G0:** inspect real repo & verify existing generator features, actual Bun/Cargo scripts. Copy kit without overwriting in-progress tasks. Human reviews module map and security boundary.
- **Gate G1:** pack validator schema/negative tests pass; judge core comparison unit + property tests pass; schema fixtures executable in disposable PG.
- **Gate G2:** end-to-end vertical slice on local PostgreSQL proves Run vs Submit, true/false verdict, SQLite persistence; no real external DB changes.
- **Gate G3:** environment lifecycle/reset/cancel/import atomicity pass negative security tests incl. forged delete and crash reconciliation.
- **Gate G4:** external PG+MSSQL read-only connectors and TLS/permissions tests pass against disposable engines; no unsafe external admin feature.
- **Gate G5:** build artifacts proven independently on target platforms; bundled runtime claimed only if actually included and tested.

## Major design risks
| Risk | Mitigation |
|---|---|
| DB sandbox escapes via arbitrary SELECT | Dedicated PG runtime, restricted runner role/OS sandbox, SQL policy and resource limits; real exploit tests |
| External user data inadvertently dropped | Managed marker/ledger + operation-scoped privileges, deny external destructive API |
| AI-generated reference wrong | Fixtures + alternate/wrong solutions + validator + independent editorial review |
| Hidden tests readable offline | State limitation; do not claim secure competitions |
| PG runtime packaging across six artifacts | Split release-runtime work; preinstalled runtime development mode documented |
| Bun / scaffold drift | Inspect generated versions first, preserve lockfiles/UI/CI, no re-scaffold |
| Multiple agents touch same migration | Single owner/task, serialized edits, worktrees and review |

## Nonnegotiable scope decisions
- MVP only read-query problems; DML/DDL judged exercises are separate enhancement requiring stronger sandbox.
- External connection explorer is read-only; future external writable sandbox must be explicitly opt-in and verified.
- `judge-core` independent of all UI / database drivers.
- `pack.json` and `problem.json` v1 contracts strict, changes require versioning/ADR.
